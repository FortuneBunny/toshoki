# 建設要素の追加計画（需要施設・交易所・道を敷く）

Trade Empires（2001）の建設要素のうち、糖商記の柱に合う3つを順に入れる。最終的に3つすべてを入れる。

- 作成日: 2026-10-20
- 前提: 本編（`docs/PLAN.md`）は完成・公開済み。全員テスト3回で調整済みのバランスを、なるべく崩さずに足す。

## 0. ねらいと柱との関係
原作では、町も道も施設もプレイヤーが作り、それを交易でつなぐ。糖商記は今、町と道が最初から決まっていて、プレイヤーが選べるのは「何をどこへ運ぶか」と工房だけ。

| 追加するもの | 柱 | 何が増えるか |
|---|---|---|
| A. 需要施設（寺院・宮殿など） | 柱2 町を育てる手応え / 柱1 判断 | 売り先を自分で作る。贅沢品の行き先が生まれる |
| B. 交易所（新しい町を開く） | 柱2 / 柱5 自動化の先の判断 | 地図そのものを広げる。中盤以降の「次の一手」 |
| C. 道を敷く | 柱1 | ルートを自分で設計する |

全員テストで繰り返し出た「定期便を組んだら待つだけ」（1〜3回目すべて）への、根本的な答えにもなる。自動化した先に、投資して地図を変えるという次の判断が待つ形。

## 1. 順番
1. **A. 需要施設**（今の「寄進」と工房の延長。影響が町の中で閉じるので、最初に入れやすい）
2. **B. 交易所**（町が増えるので、地図・セーブ・経路探索に手が入る。A の施設を新しい町にも建てられる）
3. **C. 道を敷く**（B で町が増えると、つなぐ道が欲しくなる。順番として自然）
4. **統合**: シナリオとフリープレイに組み込み、全員テストで確かめる

各段階の最後に、ボットの回帰（全シナリオで放置では達成できないこと、既存の目標が崩れていないこと）と、Claude だけの小テストを行う。全部入れ終えたら全員テスト（4回目）を行う。

---

## 2. A. 需要施設
### ルール
- 町に建てる施設。建てると、その町に**新しい需要**が生まれる（特定の品を毎日一定量ほしがる）。
- 求める品が届いている間は、その町の**成長が加速**し、評判も少しずつ上がる。届かなければ効果はない（建てっぱなしでは育たない＝柱2の「交易で育つ」を守る）。
- 1つの町に同じ種類は1つまで。建てるには、その町に自分の商人がいるか、定期便が回っていること（工房と同じ条件）。
- 費用は建設時だけ（維持費は町が持つ）。家訓「人望」の寄進の代償とは別。

| 施設 | 建てられる町 | 求める品 | 満たされたときの効果 |
|---|---|---|---|
| 茶館 | 村以上 | 茶・菓子・水飴 | 成長 +10%、甘味の需要が少し増える |
| 寺院 | 町以上 | 蜂蜜・果実酒・菓子（供物） | 成長 +15%、評判 +1/日 |
| 学問所 | 町以上 | 茶・陶器・塩 | 成長 +10%、「暮らしの豊かさ」を底上げ |
| 宮殿 | 都市以上 | 絹・香辛料・砂糖細工 | 成長 +20%、その町の贅沢品の買値が上がる（高く売れる） |

### 中身の変更
- `src/data/buildings.js` に `DEMAND_BUILDINGS` を追加（求める品、1日の量、町の段階の条件、効果）。
- `city.demandBuildings`（施設の一覧）と `city.civic`（満たされた度合い 0〜1）を追加。
- `city.js`: `dailyDemand` に施設の需要を加える。`consume` で施設分の充足率を計算し、`growthRate` に反映する。甘味は糖度にも効く（ラッシュとの関係に注意）。
- `actions.js`: `buildCivic(world, cityId, type)`。

### 画面と CLI
- 町パネルの「この町でできること」に施設のボタン。町の画面に、求める品と充足率を表示する。
- 地図の町の横に施設の小さなアイコン。
- CLI: `civic <種類> [confirm] [--at 町]`、`city` に充足率を表示する。
- SVG: 茶館・寺院・学問所・宮殿（サブエージェントに `assets/STYLE.md` で依頼。町と建物のサイズ 128×128）。

### バランスの確認
- 放置では効果ゼロ（品が届かないため）であること。
- 宮殿の「高く売れる」が必勝法にならないか（ボットの known で、宮殿の町だけに売る戦略が飛び抜けないか）。
- 町の成長の目標（s2、s4、s5、s8）が、施設で簡単になりすぎないか。A の時点で、主要な目標の達成日数が2割以上縮むなら効果を弱める。

## 3. B. 交易所（新しい町を開く）
### ルール
- シナリオごとに、地図上に**交易所の候補地**がある（オアシス、鉱山、漁場など）。最初から地図に点線の印で見えるが、まだ町ではない。
- 候補地に隣接する町に自分の商人がいると、交易所を開ける（費用 400〜800 銀。候補地ごとに違う）。
- 開くと、人口60ほどの「集落」が生まれ、候補地の資源（例: 塩6/日、鉄2/日）を産み始める。隣接する町との間に小道が1本できる。
- 新しい町も、食べ物を届ければ育ち、A の施設も建てられる。
- 候補地は限られる（シナリオに2〜4か所）。どこを開くかが判断になる。

### 中身の変更
- シナリオ定義に `sites: [{ id, name, x, y, produces, link: [隣接する町], cost, tags }]` を追加。
- `actions.js`: `foundPost(world, siteId)`。`world.cities` と `world.edges` に追加し、`hopDistance` を作り直す。
- セーブ: 町と道はすでに `world` に保存しているので、そのまま残る。`SAVE_VERSION` を 2 に上げ、版1のセーブは読み込み時に `sites` の状態を補う（移行関数）。
- 知識・ライバル・事件: 町が増えても動くこと（町の一覧を固定で持っている箇所を洗い出す）。

### 画面と CLI
- 地図: 候補地を点線の円と資源アイコンで描く。クリックで「交易所を開く」。開いたら集落の絵に変わり、演出（ファンファーレと家の出現）を出す。
- CLI: `sites`（候補地の一覧）、`found <候補地> [confirm]`。

### バランスの確認
- 新しい町の資源で、既存の相場が崩れすぎないか（候補地の生産量は控えめに）。
- 町を開くこと自体が、目標の近道になりすぎないか（例: s4 で塩の候補地を開いたら、オアシスの成長が楽になりすぎる、など）。

## 4. C. 道を敷く
### ルール
- 2つの町を結ぶ**新しい小道**を作れる。
- 条件:
  - 直線距離が一定以内（地図上で 300 以内）
  - 海を横切らない
  - 同じ2つの町の間にはまだ道がない
- どちらかが砂漠の町なら砂漠の道になる。危険度は周りの道に合わせる。
- 費用は距離に比例（距離 × 8 銀）。シナリオごとに作れる本数に上限（`maxNewPaths`、例: 2〜4本）。
- 既存の「小道を街道に整備」と組み合わせられる（荷車の通り道を自分で設計する）。

### 中身の変更
- `actions.js`: `buildPath(world, a, b)`。交差判定は海の多角形（`scenario.shapes`）との線分交差で行う。
- 経路探索・地図の描画・ボットが、途中で増える道に対応すること。

### 画面と CLI
- 地図に「道を引く」モード（町を2つ選ぶ → 費用と日数の短縮見込みを表示 → 決定）。
- CLI: `path <町A> <町B> [confirm]`。見積もりでは「今の最短日数 → 道を敷いた後の日数」を出す。

### バランスの確認
- 遠回りを強いる地形の意味（砂漠越え、s4 の主題）が消えないか。s4 では本数の上限を 1 にするか、砂漠の町どうしは結べないようにする。

## 5. 統合（シナリオとフリープレイ）
| シナリオ | 追加するもの |
|---|---|
| s1, s2 | 追加なし（導入のまま） |
| s3 糖蜜の煙 | A（茶館）だけ。工房の次の段階として、手引きに1行 |
| s4 砂の海 | B: 塩の候補地、オアシスの東の泉。C: 上限1本 |
| s5 甘い熱狂 | A（寺院・茶館）: 甘味の売り先と、ラッシュの準備 |
| s6 季節風の港 | B: 小島の候補地（港）。A（学問所） |
| s7 白い黄金 | A（宮殿）。B: サトウキビの候補地をライバルと奪い合う |
| s8 グルコース・ロード | A・B・C すべて |
| フリープレイ | A・B・C すべて。候補地も乱数で生成 |

- 新しい仕組みは、それを初めて使うシナリオで「安全な状況で手引き付きで触らせる」（ギミック学習の原則）。A は s3、B は s4、C は s4 の手引きに入れる。
- ルール説明（`src/data/help.js`）、README、CLI の help を更新する。

## 6. テスト
- **単体テスト**: 施設の需要と成長への反映、交易所を開いたあとの町・道・セーブとロード、道の条件（距離・海・重複・上限）。
- **ボット**: 全シナリオで放置では達成できないこと。既存の目標の達成日数が、追加前と比べて大きくは縮まないこと（2割以内）。goal ボットに「施設を建てる」「交易所を開く」を足し、使えば少し有利になる程度か確かめる。
- **ブラウザの自己テスト**: 施設を建てる、交易所を開く、道を引く、の3つの流れを `selftest.js` に追加する。
- **プレイテスト**:
  - 段階ごとに Claude だけの小テスト（A: s5、B: s4、C: s8）。
  - 全部入れ終えたら全員テスト4回目（Gemini の許可設定が直っていれば6人）。
  - 確かめたいこと:
    - 「定期便を組んだら待つだけ」が減ったか
    - 建設の判断が楽しいか
    - 必勝法がないか
    - 初心者が序盤で迷わないか

## 7. 危険と対策
| 危険 | 対策 |
|---|---|
| 成長の目標が簡単になりすぎる | 施設は「品が届いているときだけ」効く。段階ごとにボットで達成日数を比べる |
| 町と道が増えて、経路探索や描画が重くなる | 町は多くて15程度。Dijkstra は今の実装で十分だが、段階 C の後に計測する |
| 古いセーブが読めなくなる | `SAVE_VERSION` 2 と移行関数。版1のセーブで読み込みテスト |
| 画面がごちゃつく | 候補地と施設は小さなアイコンで描く。町パネルは「できること」にまとめる |
| 初心者が新しい要素で迷う | 手引き付きで1つずつ出す（s3 → s4 → s8） |

## 8. 完了の定義
- A・B・C がブラウザ版と CLI 版の両方で使える。
- 単体テストとブラウザの自己テストが通る。
- 全シナリオのボット回帰で、放置では達成できず、既存の目標が大きく簡単になっていない。
- 全員テスト4回目で、建設が「楽しい判断」として評価され、必勝法の報告がない（あれば直す）。
- `docs/balance-log.md`、`playtests/round-4.md`、README を更新し、公開ページに反映する。
