## 1. ゲームの柱（デザインピラー）
バランス調整やプレイテストの感想で迷ったときは、**必ずここに立ち返る**。柱を壊す変更は、どれだけ要望が多くても採用しない。

1. **読みが当たる快感**: 古い情報から相場を読み、運び、当てる。判断の余地がない仕組み（いつも同じ答えになる最適解）は柱を壊す。
2. **町を育てる手応え**: 自分の交易で町の「糖度」が上がり、町が育ち、新しい需要が生まれる。
3. **甘い誘惑とその代償**: 甘味は短期の熱狂（シュガーラッシュ）を生むが、やりすぎると反動（シュガークラッシュ）が来る。安定した成長と一時の大儲けの間で、常に選択を迫る。
4. **ドーパミンが出る手触り**: すべての行動に、即時で、気持ちよく、ときどき予想を上回る見返りがある。
5. **作業は自動化で卒業させる**: 同じ操作の繰り返しが10回を超えるようなら、それは自動化の手段を渡す合図。

## 2. 世界観：「グルコース」を軸にする

### 舞台
架空の大陸に伸びる交易路「**グルコース・ロード（糖の道）**」。シルクロードとインド洋の交易（古代〜中世）を下敷きにする。
この世界では、**町は糖で動いている**。人々の活力も、祭りも、文明の発展も、すべてはどれだけ糖（エネルギー）が届くかで決まる。
プレイヤーは小さな**商家の一族**の当主として、糖の流れをつくり、町を育て、一族を大商家へ押し上げる。

### 世界観とルールの対応
| ルール | 世界観での説明 |
|---|---|
| 町ごとに**糖度ゲージ**（その町の血糖値）がある | 町は糖で動く生き物。糖が足りなければ痩せ、満ちれば育つ |
| 糖度が低いと人口が減り、適正なら成長する | 飢えと豊かさ |
| 甘味を大量に入れると**シュガーラッシュ**（祭り、需要と価格が上がる、成長ボーナス） | 甘味がもたらす熱狂 |
| ラッシュの後に糖度が急落する**シュガークラッシュ**（甘味の需要が暴落、成長が止まる） | 熱狂の反動 |
| 隊商は移動中に食料（なつめやし、干し果物）を消費する。足りないと遅れ、倒れる | ラクダや人も糖で動く |
| 相場情報は時間とともに古くなる | 噂は旅人の足でしか届かない |
| 船の進める向きは季節で変わる | 季節風（モンスーン） |
| 精製するほど糖度が高く、高く売れる | サトウキビ → 糖蜜 → 粗糖 → 白糖 → 菓子 |

### 品物（完成時の想定。最小版はこのうち5種類）
| 区分 | 品物 | 糖の性質 |
|---|---|---|
| 主食 | 麦、米、キビ | ゆっくり安定して糖度を上げる |
| 果実 | なつめやし、ぶどう、干し果物 | 中くらい。隊商の食料にもなる |
| 甘味の原料 | サトウキビ、蜂蜜、てんさい | 加工の原料 |
| 加工品 | 糖蜜、粗糖、白糖、水飴（麦芽から作る） | 糖度が高い |
| 贅沢品 | 菓子、砂糖細工、果実酒 | 糖度が急上昇する（ラッシュの引き金になる） |
| 非糖の品 | 絹、陶器、香辛料、茶、塩、木材、鉄 | 町の段階が上がると需要が出る。加工の材料にもなる |

### 見た目の方向性
- 砂色、琥珀色、蜂蜜色を基調にする。糖の結晶のきらめき（白とシアンのハイライト）を差し色にする。
- 夜の画面や暗い背景の上では、糖の結晶が光るように見せる。

## 3. 遊びの構造

### コアループ（30秒〜2分）
```
相場を見る（情報は古いかもしれない） → 仕入れる（交易画面） → 運ぶ（道中の消費と危険）
      ↑                                                              ↓
  次の行き先を決める ← 利益の演出 ＋ 町の糖度の変化 ← 売る（交易画面）
```

### ミドルサイクル（数十分）
- 儲かるルートを見つけたら**定期便**にして自動化する。条件は「○銀以下で買う」「○銀以上で売る」の2つだけ。
- 商人を雇う。ロバからラクダ、荷車、ダウ船へと輸送手段を乗り換える。
- 工房（製糖所、菓子工房など）や道路、港を建てる。
- 町を育てる: 集落 → 村 → 町 → 都市 → 大都市。段階が上がると新しい需要が出る。

### マクロサイクル（数時間）
- シナリオの目標を達成する。
- 技術が進み、新しい品や輸送手段が手に入る。情報の届く速さも上がる（駅伝制 → のろし → 新聞 → 電信）。
- 一族が代替わりし、家訓（シナリオをまたいで使える特典）を1つ受け継ぐ。

### キャンペーン（8シナリオ＋フリープレイ）
新しいギミックは「安全な状況で一度触らせてから、本番に置く」順で出す（レベルデザインの「ギミック学習」）。

| # | 題名 | 新しく出るもの | 目標の例 |
|---|---|---|---|
| 1 | はじまりの甘み | 町2つ、品物2つ、売買のみ（チュートリアル） | 銀を500にする |
| 2 | なつめやしの谷 | 相場の変動、情報が古くなる、糖度ゲージ | 村を1つ町に育てる |
| 3 | 糖蜜の煙 | 加工（工房）、定期便 | 白糖を月に100個作る |
| 4 | 砂の海 | 砂漠越え、隊商の食料消費、盗賊と護衛、オアシス都市 | オアシスまでの交易路を開く |
| 5 | 甘い熱狂 | シュガーラッシュとクラッシュの本格的な管理、祭り | ラッシュを3回起こしつつ人口を減らさない |
| 6 | 季節風の港 | 船、季節風、港の建設 | 海の向こうの町と定期便を結ぶ |
| 7 | 白い黄金 | ライバル商家（台本付き）、市場の取り合い | 白糖の取引量で首位になる |
| 8 | グルコース・ロード | 全要素、大きな地図 | 大陸を貫く交易網で首都を大都市に |
| ∞ | フリープレイ | 乱数で生成する地図 | スコアのやり込み |

## 4. ドーパミン設計（演出と報酬）
狙いは「次の一手をやりたくてたまらない」状態。ただし**柱1（読みの快感）を報酬で置き換えない**。演出は判断の結果を気持ちよく伝えるためのもので、判断そのものを不要にはしない。

### 即時の報酬（毎回の取引）
- 売った瞬間に `+128 銀` が浮かび上がり、所持金が**カウントアップ**する。コインの音は利益が大きいほど高い音になる。
- **予想を上回ったとき**（売値が最後に見た相場より高かったとき）は「読み的中！」と出し、糖の結晶が弾けて画面が少し揺れる。
- 町の糖度ゲージが**ぐっと伸びる**アニメーションを入れる。成長の閾値を越えたら光る。

### 変動する報酬（ときどき起きる驚き）
- **大口注文**: 町からランダムに依頼が来る（「3日以内に蜂蜜30」）。期限付きで報酬が大きい。
- **相場の急騰**: 飢饉、祭り、婚礼などの事件。噂として流れる。
- **掘り出し物**: 珍しい品（金色に光るアイコン）がまれに市場に出る。
- **連続黒字**: 黒字の取引が続くと評判の倍率が上がり、効果音の音程も段階的に上がる。赤字が出ると途切れる。

### 進捗の報酬（ミドル、マクロ）
- 町の段階が上がるとファンファーレが鳴り、町の絵が変わる（集落から大都市まで、5段階のSVG）。
- 目標の達成度は常に画面上部に表示する。あと少しで届くと分かると、人はやめられなくなる。
- 実績バッジ、一族の家系図、シナリオごとのS〜Cランク評価。

### 実装の原則
- 効果音は WebAudio で合成する（音声ファイルは不要）。
- 演出の強さは設定で3段階に変えられるようにする。`prefers-reduced-motion` に従う。
- 演出は大きい出来事ほど派手にし、小さい出来事は控えめにする（すべてを派手にすると何も目立たなくなる）。

## 5. 技術構成

### 方針
- **素のHTML、CSS、JavaScript（ESモジュール）。ビルドなし**。そのまま GitHub Pages に載せられる。
- **ゲームの中身（シミュレーション）と画面を完全に分ける**。中身は Node でもブラウザでも同じコードで動かす。これでCLI版とプレイテストができるようになる。
- 乱数は**シード付き**にする。同じシードと同じ操作なら、必ず同じ結果になる（プレイテストの比較と再現のため）。
- 時間は**1日を1単位**として進める。ブラウザでは一時停止、1倍、2倍、4倍の速度で自動進行する。CLIではコマンドで進める。
- テストは `node --test` を使う（外部依存なし）。

### 価格モデル（初期案。調整はプレイテストで行う）
- 基準価格 × 需給補正。需給補正は在庫と、町の需要（人口 × 段階 × 糖度による係数）の比から決める。
- **取引量による価格の動き**: 1個売り買いするごとに在庫が変わり、価格をその都度計算し直す。交易画面では合計額を正確に表示する。
- 町は毎日、品物を生産し消費して、在庫が平衡状態に戻ろうとする。これが価格の回復速度になる。
- 自分の町で売るときと買うときの価格には差（手数料）を付ける。差がゼロだと、同じ町での往復で儲けられてしまう。

### 糖度モデル（初期案）
- 糖度 = 0〜200。毎日「人口 × 消費係数」だけ減り、品物が消費されると「その品の糖量」だけ増える。
- 40未満で飢え（人口が減る）、40〜110で安定（成長する）、110〜150で活況（成長が加速し、贅沢品の需要が上がる）。150を超えると**シュガーラッシュ**（数日間、祭りが続き、価格が高騰する）。
- ラッシュが終わると**クラッシュ**（数日間、糖の消費効率が落ち、甘味の需要が暴落する）。

## 6. CLI版（人間とAIが遊べるテキスト版）

### 方針
- **1回の実行で1コマンド、状態はセーブファイルに保存**する形にする。AIエージェントが Bash から1手ずつ遊べるようにするため。
- 対話モード（REPL）も用意し、人間が続けて遊べるようにする。
- 出力は人間向けの表形式と、`--json` を付けたときの機械向けJSONの2種類。

### コマンドの例
```
node cli/glucose.js new --scenario 2 --seed 42 --save run.json
node cli/glucose.js --save run.json status          # 日付、所持金、目標の進み具合、商人の状態
node cli/glucose.js --save run.json market          # 今いる町の相場（交易画面と同じ情報）
node cli/glucose.js --save run.json prices          # 知っている全部の町の相場（情報の古さ付き）
node cli/glucose.js --save run.json quote buy dates 30   # 30個買ったらいくらになるか（確定はしない）
node cli/glucose.js --save run.json trade buy dates 30 sell grain 10   # 交易画面の確定と同じ
node cli/glucose.js --save run.json travel oasis    # 移動を始めて、到着するか事件が起きるまで日を進める
node cli/glucose.js --save run.json wait 3
node cli/glucose.js --save run.json city oasis      # 糖度、人口、需要
node cli/glucose.js --save run.json order add ...   # 定期便
node cli/glucose.js --save run.json ledger          # 帳簿
node cli/glucose.js help
```
- 演出はCLIでも文字で出す（`★ 読み的中！ +128 銀（予想より +34）`、`🎉 オアシスが「町」に成長した！`）。
- 全コマンドを `playtests/raw/<run>.jsonl` に記録する。あとで集計できるようにするため。

## 7. SVG素材の制作（サブエージェント）

### 手順
1. **スタイルガイドを先に作る**（`assets/STYLE.md`）。
   - 配色（色コードで指定）、線の太さ、角の丸み、光の向き（左上から）
   - アイコンは `viewBox="0 0 64 64"`、町は `0 0 128 128`
   - 外部参照、`<script>`、埋め込みラスター画像は禁止
2. **カテゴリごとにサブエージェントへ分担**し、並行して作る。各エージェントにはスタイルガイドと担当リストだけを渡す。
   | 担当 | 内容 | 数（最小版 → 完成時） |
   |---|---|---|
   | A | 品物のアイコン | 5 → 約25 |
   | B | 町の5段階、工房、港、隊商宿 | 5 → 約12 |
   | C | 輸送手段（ロバ、ラクダ、荷車、ダウ船、大型船）、商人の顔 | 2 → 約10 |
   | D | 地形（砂漠、オアシス、山、川、海、草原）、UI部品（銀貨、糖の結晶、ゲージ、パーティクル） | 約10 → 約20 |
3. `tools/validate-svg.js` で検証する。XMLとして正しいか、viewBox があるか、禁止要素がないか、ファイルサイズが目安以下か。
4. `tools/contact-sheet.html` で一覧を表示し、ヘッドレスのブラウザでスクリーンショットを撮って統一感を確認する。外れた素材はやり直す。
5. 地図の背景は素材ではなく、地形データからコードで描く。

## 8. プレイテスト（AIエージェントに遊ばせる）

### 3段階の腕前
| 腕前 | 使うモデル | 呼び出し方 |
|---|---|---|
| 上手い | Opus、Codex Sol 6.1 | Agent ツール（`model: opus`）、`codex exec -m gpt-6.1-sol` |
| そこそこ | Sonnet、Gemini 3.8 Flash | Agent ツール（`model: sonnet`）、`agy --model gemini-3.8-flash-medium -p ...` |
| 下手 | Haiku、Codex Luna 6 | Agent ツール（`model: haiku`）、`codex exec -m gpt-6-luna` |

- Codex のモデルIDは `gpt-6.1-sol` と `gpt-6-luna`（確認済み）。`codex exec --skip-git-repo-check --ephemeral -s workspace-write -C <作業ディレクトリ>` で動かす。
- Gemini は Antigravity CLI（`agy`）から呼ぶ。`agy models` で `gemini-3.8-flash-high/medium/low` が使えることを確認済み。
  標準は medium を使う。`--output-format json` で結果を受け取る。
- Codex と agy のテスターも、Claude のテスターと同じプロンプトと同じルール（ソースを読ませない、作業ディレクトリを限定する）で動かす。
  権限を自動承認するオプションは、ゲームのコピーを置いた専用ディレクトリの中でだけ使う。

### プレイテストの規模（2段構え）
| 種類 | いつ | 誰が | 規模 |
|---|---|---|---|
| **全員テスト** | 大改修の区切りだけ（下の一覧） | 6人全員（3段階 × Claude系とそれ以外） | 対象シナリオすべて |
| **小テスト** | 細かい変更の確認（数値の調整、UI文言、ギミック1つの追加など） | Claude だけ（Opus、Sonnet、Haiku）。変更に関係する腕前だけに絞ってもよい | 関係するシナリオ1つ |
| **ボット** | 数値を変えるたびに毎回 | `tools/sim-bots.js` | 数百回 |

全員テストを行う区切り:
1. フェーズ2の終わり（中心となる遊びの検証）
2. 中身のルールを大きく変えたとき（価格モデル、糖度モデル、情報の古さの仕組みなど）
3. フェーズ6の終わり（全シナリオがそろったとき）
4. フェーズ7の最後の周回（公開前の最終確認）

小テストの結果だけで大きな方針は変えない。方針が揺らぐ兆しがあれば、全員テストで確かめてから判断する。

- モデルの実力差をそのまま使う。加えて、プロンプトでそれぞれの腕前らしい遊び方をさせる。
  - 上手い: 最適化を狙う、抜け道を探す
  - そこそこ: 普通に楽しむ
  - 下手: 説明をあまり読まず直感で動く、ミスもする
- **テスターにはソースコードを読ませない**。渡すのはCLIの `help` とゲーム内の説明だけ（実際のプレイヤーと同じ条件にするため）。作業ディレクトリをゲームのコピーに限定する。
- 同じシナリオと同じシードで遊ばせて、腕前ごとに比べる。

### テスターが出すもの
- 自由記述の感想。特に、面白かった瞬間、退屈だった瞬間、迷った瞬間。
- 決まった形式の評価: 楽しさ、分かりやすさ、もう一度やりたいか（各1〜5）、難しさ（1〜5）、一番気持ちよかったこと、一番イライラしたこと、使った戦略。
- 生ログ（コマンドの記録）から自動集計する数値: クリアできたか、かかった日数、時間あたりの利益、赤字取引の割合、使った機能、迷って同じコマンドを繰り返した回数。

### 難易度の目標（シナリオごとの目安）
| 腕前 | 目標 |
|---|---|
| 上手い | 余裕でクリアし、Sランクを狙えるが、Sには工夫が要る |
| そこそこ | ときどき苦戦しつつクリアする。B〜Aランク |
| 下手 | 序盤（シナリオ1〜3）は必ずクリアできる。後半は失敗もあってよいが、**負けた理由が本人に分かること** |

### 感想の振り分け（言いなりにならないためのルール）
1. 感想を **バグ / 分かりにくさ / バランス / 好みの問題 / 柱と衝突するもの** に分ける。
2. 腕前によって、読み方を変える。
   - **下手な人が詰まった** → まず分かりにくさ（説明、フィードバック、誘導）を直す。難易度を下げるのは最後の手段。
   - **上手い人が必勝法を見つけた** → 必ず潰す（柱1「判断の余地」を壊しているため）。
   - **そこそこの人が退屈した** → テンポとミドルサイクルの報酬を見直す。
3. **複数のテスター、または数値の裏付けがある問題だけ**を直す。1人だけの好みは記録して保留する。
4. 柱と衝突する要望は採用しない。例:「相場を全部見せて」は柱1を壊す。「ラッシュの反動をなくして」は柱3を壊す。
   ただし、その要望の**裏にある不満**（例: 情報が古すぎて読めない）には別の手段で応える。
5. 直すときは、ルールより先に**数値**を触る。数値で直らないときだけ仕組みを変える。
6. 変えたこと、採用しなかった要望、その理由をすべて `docs/balance-log.md` に残す。

### 補助：決まった戦略で遊ぶボット
`tools/sim-bots.js` に決まった戦略のボットを用意し、数百回まわして数値を素早く確認する。AIテスターより安く速い。
- 例: 貪欲ボット（今一番儲かる品を運ぶ）、ランダムボット、甘味だけを運ぶボット
- **甘味だけのボットが最強になったら、柱3が壊れている**サイン。
